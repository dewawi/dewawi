# K1 team calendar, K2 reminders, K3 invitations and K4 usability

Run `python3 tests/calendar/run.py` from the repository root. The suite creates a disposable MariaDB with networking disabled, a local PHP HTTP fixture and a loopback-only SMTP capture server, then exercises the real calendar model, controller, forms, views, shared layout, jQuery and global scripts. Chromium checks desktop (1280 px) and mobile (390 px) interactions. SMTP fixtures simulate successful acceptance, rejection and a connection loss after DATA. No real account configuration, database or outbound email delivery is used. Attachment copies are written only below the disposable directory. The services and temporary databases are removed when the runner exits.

Also run `python3 tests/install/import-db.py`, the existing permission/authentication/client-switch/profile/admin security tests, `python3 tests/ui/notifications.py`, and PHP syntax checks on the changed PHP/templates.

## Implementation

- `/calendar` is a standard ZF1 module, with `calendar.index` permissions in the existing user permission editor. The header link requires view permission. Creating users and fresh installation use the existing default-permission convention. Upgrades preserve existing permissions; an administrator explicitly enables calendar access.
- Every calendar model operation uses the authenticated actor and selected tenant. The existing parent/child sharing of contacts and products does not share calendars. Users who legitimately switch tenants may own appointments in the selected tenant. Event and participant management require ownership, including for administrators; invitees may change only their own response.
- Private foreign events expose only their busy interval, owner and calendar metadata. Active internal invitees may read the event details and participant names/statuses; other participants' addresses are restricted to the organizer. SQL masks title, description and location before presentation. The same projection serves HTML and JSON. Deleted appointments are excluded. There is no separate search/export path with access to raw events.
- Calendar forms reuse `DEEC_Form` and the existing session-token/`hash_equals` CSRF pattern. Start and end are saved in one explicit POST with `data-autosave="false"`; the general edit-lock keepalive does not apply to the calendar. GET never creates or deletes an appointment. Owner and tenant cannot be submitted or reassigned.
- New events retain local `start`/`end` and the IANA timezone, with authoritative `startutc`/`endutc` instants. Nonexistent local times are rejected. Ambiguous times require the earlier/later choice, which survives editing. Seconds are preserved. All-day events use local calendar dates and an exclusive end date, so a day remains one date across DST or display-zone differences.
- The existing `calendarevent` table and active `update-1.1.7-1.1.8.sql` migration are extended. `structure.sql` has matching columns/indexes; `data.sql` grants the initial user the same defaults as new users. The installer test executes the complete active migration against its pre-upgrade fixture.
- K2 reminders use the existing calendar model and the appointment row; there is no separate notification queue, delivery worker or generic notification framework. K3 reuses the calendar module, `DEEC_Form`, jQuery, personal SMTP configuration, `DEEC_Email` and the existing private email/attachment archive. No new subscription model or entitlement bypass is introduced.

## Upgrade and operational notes

Apply the added K1/K2/K3 blocks in `install/config/update-1.1.7-1.1.8.sql` using the normal controlled update process before using this module. No database update is performed by the implementation task. If 1.1.8 was already applied, apply only the previously unapplied statements after inspecting the schema; do not rerun the complete migration blindly. The added ALTER statements are not designed for repeated execution. If K1 is installed, apply K2 and K3; if K1/K2 are installed, apply only the final block starting `-- K3 participants`. For a partially applied K3 block, inspect the four new `calendarevent` columns and `icaluid` unique key, the complete `calendarparticipant` table/keys/foreign key, and the five nullable `emailmessage` columns plus `calendar_delivery` unique key. Apply only missing ADD statements, complete the table/indexes, and backfill only NULL UIDs using the provided UPDATE. Never regenerate existing UIDs. Existing appointments default to no reminder; K3 preserves appointment times, permissions and reminder state. New installations use the synchronized `structure.sql` directly.

Legacy events keep their original wall times, are private by default and receive `createdby` as owner. Their timezone was never stored, so they are interpreted using the configured tenant timezone; UTC columns remain NULL until the owner explicitly saves the event. During a legacy ambiguous hour the busy interval conservatively covers the earlier start through the later end. Verify historically uncertain timezones or DST values manually before relying on them. Events with no recorded creator remain ownerless and require a deliberate administrative data correction to assign ownership. No automated reassignment or historical time conversion is attempted.

Regular users need at least `view` plus the relevant `add`, `edit` or `delete` permissions. Enable them under Settings → Users → Permissions → Calendar. Existing calendar permissions remain unchanged. All-day end dates are exclusive. Mobile month/week views become a readable daily list. The fixture covers MariaDB; a separate MySQL server was not available for runtime verification.

## K2 reminder behavior

The appointment form offers none (default), at start, 5/15/30/60 minutes before, or 24 hours before. An omitted `reminderminutes` field in an older full-event API request preserves the existing choice. All-day reminders use the first existing instant of that date in the event timezone. A day before means exactly 24 UTC hours, including across DST; the option says so explicitly.

`reminderminutes`, `reminderdue`, `reminderdone` and `reminderrevision` hold one persistent state per appointment. GET polling never writes or creates reminder records. Overdue reminders remain available after a session absence until completed, snoozed, disabled, rescheduled or deleted; they do not silently expire at the event end. Snooze adds 5/15/60 minutes to the server's current UTC time.

Changing start/end instants, timezone, all-day status or reminder offset rearms the reminder and clears completion/snooze. Text/location/visibility changes preserve completion and snooze. Event saves lock the owned tenant-scoped row and increment the revision. Completion/snooze uses one atomic UPDATE constrained by owner, tenant, non-deleted state, due time and expected revision. Concurrent/repeated/stale actions return 409 and refresh the list instead of duplicating or extending state changes. An edit racing with an acknowledgement cannot swallow the new schedule. The appointment ID remains the unique reminder identity.

The reminder endpoint `/calendar/index/reminders?context=<user>:<selected-tenant>` requires the existing calendar view permission. Only the current owner's reminders are returned or changed. Personal completion/snooze does not grant event editing rights; configuring a reminder retains normal create/edit permission checks. POST additionally checks the existing user/tenant-scoped calendar CSRF token, an explicit operation and an allowlist of input fields. GET cannot mutate state. All responses have private/no-store caching. Old pages cannot retrieve the newly selected user's or tenant's reminder content. Header context uses the selected user tenant even while another module legitimately shares parent data.

The existing top menu renders the bell only for calendar readers. A dropdown opens exclusively on a click; the count uses a static highlight. Up to 20 reminders are shown, with the complete open count and an explicit note when more remain. Entries and count are replaced from the server, and title rendering uses DOM text rather than HTML. Links open the existing calendar detail page. Completion and snooze update the menu through AJAX without a page reload.

A single 60-second timer runs only while the authenticated page is visible, online and has had activity in the last five minutes. It pauses when hidden, offline, idle or placed in the page cache, and resumes on activity/focus/visibility/online/pageshow. Transient errors back off to a maximum of five minutes. Requests never overlap within a page. Opening the bell explicitly refreshes the list. A 401/403 or mismatched response context clears private content and stops polling until the page is reloaded; background failures do not invoke the existing foreground 401 reload handler. There are no automatic popups, modal dialogs or browser notifications.

The K2 suite adds independent database workers for real simultaneous snooze/confirmation requests and an edit/confirmation race, parallel HTTP requests, CSRF and context negatives, English/German rendering, real desktop/mobile header interactions, and a deterministic Chromium transport/clock for polling, network backoff and session/context termination. The migration suite compares both the complete upgrade and a K1-already-installed/K2-only upgrade with the fresh schema.

## K3 participants and explicit invitations

Owners add active users from the selected tenant, or external name/address pairs. With existing contacts read permission, a bounded search selects direct contact email addresses from the authorized contacts tenant, including existing parent sharing. The server resolves the selected address and validates it again before REQUEST delivery. It does not grant contact access to invitees. Duplicate user IDs or normalized addresses within an event are rejected. Removed entries remain available to the organizer for targeted cancellation; re-adding resets the response to invited and advances the participant generation. An internal address changed since the last invitation must first receive an explicit cancellation at its old address before that snapshot can be replaced.

`calendarparticipant` stores invited/accepted/declined status. Internal users change only their own response through authenticated CSRF-protected POST; organizers may record external replies manually. There is no public RSVP endpoint or incoming email processor. Adding a participant never confirms attendance; K4 adds the explicit email checkbox described below. Invitations appear under My calendar/My invitations with their status. Employee filters include active invitations, omitting declined attendance for other employees' availability. Invited users receive no K2 reminders and cannot edit the organizer's event. Removal revokes private-detail access immediately. Cancelled events stop reminders and remain visible to the organizer and existing invitees.

The separate explicit send action remains available for later invitations, updates and cancellations (maximum 20 per request, 100 active participants per event); its recipients remain unchecked initially. Calendar view/edit ownership and the existing add/send permission are required. The existing campaign cron is not suitable for this explicit-only workflow and is not used. Each selected recipient receives a separate localized message and a private archived `.ics`, with no implicit CC/BCC and no disclosure of other addresses. Sending reuses the organizer's personal SMTP account; the organizer email is fixed by the first prepared invitation and must match on subsequent sends.

The generator follows [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html) and the REQUEST/CANCEL rules in [RFC 5546](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.5): persistent UID, UTC DTSTAMP, monotonic SEQUENCE, UTC timed DTSTART/DTEND, local DATE values for all-day events, exclusive end, CRLF, escaped TEXT and UTF-8-safe 75-octet folding. PHPMailer includes both a text/calendar METHOD alternative and the attachment. Appointment/participant changes advance SEQUENCE; reminder-only edits and RSVP do not. Removed attendees receive only their own CANCEL. Minimal cancellation messages omit title, description, location and dates so later private changes are not exposed. STATUS:CANCELLED appears only for cancellation of the entire event. Deleting an event sends nothing: cancel, explicitly select/send, then delete when appropriate.

The existing `emailmessage` table holds a unique dispatch identity for tenant/event/participant/generation/sequence/method. The owned event row serializes reservations; independent senders can claim a pending message only once. The immutable archive is prepared in a transaction, and `sending` is committed before SMTP is attempted. Repeated requests never resend a processed identity. A stale pending sequence is marked obsolete. Errors do not undo saved appointments. Unknown SMTP acceptance (including a crash after claiming) deliberately prevents automatic retry: exactly-once delivery cannot be guaranteed across a database and SMTP. Check the organizer's mail server/outbox before any deliberate new event revision/send. An already in-flight email cannot be recalled by an edit or deletion; UID/SEQUENCE orders subsequent explicit updates/cancellations. Message history and archive reads are restricted to the tenant's organizer, excluded from generic contact history, and generic resend cannot bypass calendar deduplication.

Only the local capture server was used to verify email transport/MIME. Live SMTP accounts and behavior inside individual Outlook/Google/Apple clients were not exercised. Two-way synchronization and advanced permissions remain outside K3.

## K4 usability

The participant forms now offer “Send calendar invitation by email”. With existing send permission, JavaScript enables and checks it when an eligible address is available. Explicitly unchecking persists while editing that form. Accounts without a valid address leave it disabled; the form embeds only address availability, not a directory of user email addresses. An omitted `sendinvite` field remains equivalent to unchecked for older callers. A checked value is validated before adding, including send permission. After the participant transaction commits, the controller calls the unchanged K3 invitation sender for exactly the returned participant ID and sequence. No parallel sender or queue is introduced. The original sequence check and durable K3 dispatch identity prevent duplicate additions/delivery, including concurrent requests. An SMTP or preparation error preserves the participant and displays a saved-but-not-sent warning; unknown SMTP acceptance is never automatically retried. Native form submissions use a user/tenant-scoped, event-specific one-time notice after redirect; AJAX returns saved state and the separate mail result.

The K3 code did not reject an address merely because it existed elsewhere. It did combine self-invitation, invalid-user and invalid-name failures into `CALENDAR_PARTICIPANT_INVALID`, and it did not resolve manually entered addresses. K4 distinguishes those cases, invalid addresses, duplicates and ambiguous matches. A unique active user in the selected tenant resolves to an internal invitation; otherwise a unique readable, unsuppressed contact address resolves through existing contacts sharing. Ambiguous records require explicit selection. Other tenants and inaccessible contacts are not searched; the same address can still be entered manually as an external participant without revealing its existence elsewhere. Native validation preserves entered values and the opt-out. Editing an address/name clears a previously selected contact ID, and the server rejects a conflicting posted contact address instead of silently using the old selection.

Changing the start date/time or fold asks the existing calendar controller's authenticated, CSRF-protected `endtime` POST action for a suggestion. The pure calendar date helper reuses the existing timezone, gap/fold and event validation functions. Timed appointments retain elapsed UTC seconds, including across DST; all-day appointments retain their number of calendar dates with an exclusive end. The browser uses neither its own local timezone nor an additional date library for this calculation. End time/fold edits establish the next duration; they invalidate pending suggestions, so late responses cannot overwrite manual choices. Timezone and all-day changes reset the baseline. Saving is disabled while a suggestion is pending; an error leaves the end unchanged and is shown inline. Merely opening an event never changes or saves its dates. Full server-side appointment validation remains authoritative.

No SQL changes or manual database follow-up are required for K4 on an existing K1–K3 installation. Do not rerun the K3 migration for this update.

`usability.php` covers date/time/multiday/all-day shifts, UTC duration through spring/fall transitions, ambiguous/gap times, seconds, limits, user/contact resolution, scoped negative cases and four simultaneous add-and-send workers. `usability-workflow.py` covers checked/unchecked additions, direct K3 dispatch, rejected/uncertain SMTP, preparation failures with saved-state notices, native validation, repeated/parallel HTTP calls, CSRF and read/edit/send permissions. Its real Chromium workflows at 1280/390 px exercise both forms, immediate email, persistent opt-out, contact editing, duration changes, DST, manual-end races and create/edit persistence. The complete K1/K2/K3 suite, fresh/upgrade schema checks, existing mail/security/user tests and global UI regressions remain in use. Tests use only disposable data and loopback SMTP capture; no production email or database is used.
