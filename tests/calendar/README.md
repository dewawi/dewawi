# K1 team calendar and K2 reminders

Run `python3 tests/calendar/run.py` from the repository root. The suite creates a disposable MariaDB with networking disabled and a local PHP HTTP fixture, then exercises the real calendar model, controller, forms, views, shared layout, jQuery and global scripts. Chromium checks desktop (1280 px) and mobile (390 px) interactions. Existing configuration files and databases are never used. The services and temporary databases are removed when the runner exits.

Also run `python3 tests/install/import-db.py`, the existing permission/authentication/client-switch/profile/admin security tests, `python3 tests/ui/notifications.py`, and PHP syntax checks on the changed PHP/templates.

## Implementation

- `/calendar` is a standard ZF1 module, with `calendar.index` permissions in the existing user permission editor. The header link requires view permission. Creating users and fresh installation use the existing default-permission convention. Upgrades preserve existing permissions; an administrator explicitly enables calendar access.
- Every calendar model operation uses the authenticated actor and selected tenant. The existing parent/child sharing of contacts and products does not share calendars. Users who legitimately switch tenants may own appointments in the selected tenant. All mutations additionally require ownership, including for administrators.
- Private foreign events expose only their busy interval, owner and calendar metadata. SQL masks title, description and location before presentation. The same projection serves HTML and JSON. Deleted appointments are excluded. There is no separate search/export path with access to raw events.
- Calendar forms reuse `DEEC_Form` and the existing session-token/`hash_equals` CSRF pattern. Start and end are saved in one explicit POST with `data-autosave="false"`; the general edit-lock keepalive does not apply to the calendar. GET never creates or deletes an appointment. Owner and tenant cannot be submitted or reassigned.
- New events retain local `start`/`end` and the IANA timezone, with authoritative `startutc`/`endutc` instants. Nonexistent local times are rejected. Ambiguous times require the earlier/later choice, which survives editing. Seconds are preserved. All-day events use local calendar dates and an exclusive end date, so a day remains one date across DST or display-zone differences.
- The existing `calendarevent` table and active `update-1.1.7-1.1.8.sql` migration are extended. `structure.sql` has matching columns/indexes; `data.sql` grants the initial user the same defaults as new users. The installer test executes the complete active migration against its pre-upgrade fixture.
- K2 reminders use the existing calendar model and the appointment row; there is no separate notification queue, delivery worker or generic notification framework. K3 participants/invitations remain unimplemented. No new subscription model or entitlement bypass is introduced.

## Upgrade and operational notes

Apply the added K1 and K2 blocks in `install/config/update-1.1.7-1.1.8.sql` using the normal controlled update process before using this module. No database update is performed by the implementation task. If 1.1.8 was already applied, apply only the previously unapplied statements after inspecting the schema; do not rerun the complete migration blindly. The added ALTER statements are not designed for repeated execution. If K1 is already installed, only the K2 block (following `-- K2 calendar reminders:`) is needed. Inspect all four columns and the new index before completing a partially applied K2 block; do not rerun an already applied ADD statement. Existing appointments default to no reminder and their time values are not changed.

Legacy events keep their original wall times, are private by default and receive `createdby` as owner. Their timezone was never stored, so they are interpreted using the configured tenant timezone; UTC columns remain NULL until the owner explicitly saves the event. During a legacy ambiguous hour the busy interval conservatively covers the earlier start through the later end. Verify historically uncertain timezones or DST values manually before relying on them. Events with no recorded creator remain ownerless and require a deliberate administrative data correction to assign ownership. No automated reassignment or historical time conversion is attempted.

Regular users need at least `view` plus the relevant `add`, `edit` or `delete` permissions. Enable them under Settings → Users → Permissions → Calendar. Existing calendar permissions remain unchanged. All-day end dates are exclusive. Mobile month/week views become a readable daily list. The fixture covers MariaDB; a separate MySQL server was not available for runtime verification.

## K2 reminder behavior

The appointment form offers none (default), at start, 5/15/30/60 minutes before, or 24 hours before. An omitted `reminderminutes` field in an older full-event API request preserves the existing choice. All-day reminders use the first existing instant of that date in the event timezone. A day before means exactly 24 UTC hours, including across DST; the option says so explicitly.

`reminderminutes`, `reminderdue`, `reminderdone` and `reminderrevision` hold one persistent state per appointment. GET polling never writes or creates reminder records. Overdue reminders remain available after a session absence until completed, snoozed, disabled, rescheduled or deleted; they do not silently expire at the event end. Snooze adds 5/15/60 minutes to the server's current UTC time.

Changing start/end instants, timezone, all-day status or reminder offset rearms the reminder and clears completion/snooze. Text/location/visibility changes preserve completion and snooze. Event saves lock the owned tenant-scoped row and increment the revision. Completion/snooze uses one atomic UPDATE constrained by owner, tenant, non-deleted state, due time and expected revision. Concurrent/repeated/stale actions return 409 and refresh the list instead of duplicating or extending state changes. An edit racing with an acknowledgement cannot swallow the new schedule. The appointment ID remains the unique reminder identity.

The reminder endpoint `/calendar/index/reminders?context=<user>:<selected-tenant>` requires the existing calendar view permission. Only the current owner's reminders are returned or changed. Personal completion/snooze does not grant event editing rights; configuring a reminder retains normal create/edit permission checks. POST additionally checks the existing user/tenant-scoped calendar CSRF token, an explicit operation and an allowlist of input fields. GET cannot mutate state. All responses have private/no-store caching. Old pages cannot retrieve the newly selected user's or tenant's reminder content. Header context uses the selected user tenant even while another module legitimately shares parent data.

The existing top menu renders the bell only for calendar readers. A dropdown opens exclusively on a click; the count uses a static highlight. Up to 20 reminders are shown, with the complete open count and an explicit note when more remain. Entries and count are replaced from the server, and title rendering uses DOM text rather than HTML. Links open the existing calendar detail page. Completion and snooze update the menu through AJAX without a page reload.

A single 60-second timer runs only while the authenticated page is visible, online and has had activity in the last five minutes. It pauses when hidden, offline, idle or placed in the page cache, and resumes on activity/focus/visibility/online/pageshow. Transient errors back off to a maximum of five minutes. Requests never overlap within a page. Opening the bell explicitly refreshes the list. A 401/403 or mismatched response context clears private content and stops polling until the page is reloaded; background failures do not invoke the existing foreground 401 reload handler. There are no automatic popups, modal dialogs or browser notifications.

The K2 suite adds independent database workers for real simultaneous snooze/confirmation requests and an edit/confirmation race, parallel HTTP requests, CSRF and context negatives, English/German rendering, real desktop/mobile header interactions, and a deterministic Chromium transport/clock for polling, network backoff and session/context termination. The migration suite compares both the complete upgrade and a K1-already-installed/K2-only upgrade with the fresh schema.
